## 文档冲突处理

浏览器网页接入指南的步骤仍展示 v2 令牌示例，而 2026-06-29 更新的 v2 API 页面已明确标记“历史版本，不推荐使用”，并指向 v3。项目以新版具体 API 页面为准，统一使用：

```text
POST https://accounts.feishu.cn/oauth/v3/token
```

## 已据此冻结的产品决策

1. 默认使用管理员的 `user_access_token` 自动创建多维表格。
2. 首次接入不要求管理员手工创建表格或复制任何表标识。
3. 不把“多维表格插件”作为 OpenAPI 接入前置条件。
4. 后台持续同步申请 `offline_access`，并实现刷新令牌单次使用和原子轮换。
5. 默认申请细粒度权限，不直接申请完整 `bitable:app`。
6. 表格、数据表和记录标识由后端数据库保存，业务 ID 作为幂等键。

## 2026-08-13 二次复核（本次变更依据）

复核方式：重新抓取飞书开放平台官方文档（markdown 版与“API 权限列表”页面渲染结果），逐条核对权限键、中文名称与接口参数。

确认结果：

1. 当前 9 个权限键全部真实存在，且均支持用户身份调用；官方中文名称与项目前端展示已对齐。
2. `获取授权码` 接口（https://open.feishu.cn/document/authentication-management/access-token/obtain-oauth-code）必填参数为 `client_id`、`response_type=code`、`redirect_uri`。原实现使用 `app_id` 且缺少 `response_type`，已修正。
3. `批量获取记录` 接口（`GET .../records`）的官方权限要求为 `bitable:app` 或 `bitable:app:readonly`，不在最小权限集内。记录对账已改用 `检索记录` 接口（`POST .../records/search`，权限要求 `base:record:retrieve`），分页参数 `page_size`、`page_token` 放查询参数，`page_size` 最大 500。
4. 令牌端点、刷新轮换、自动建表、批量写入与更新的请求/响应结构经重新核对，与官方页面一致，未改动。

## 2026-08-13 生产联调记录（PKCE 移除依据）

联调现象：`state` 与授权链接均正常、回调可达，但令牌端点持续返回 HTTP 400、错误码 20049（PKCE code challenge failed）。本地复核确认 challenge 与 verifier 的 S256 计算严格匹配。

官方依据与处理：

- “获取授权码”页面将 `code_challenge`、`code_challenge_method` 标注为可选参数，其请求示例 URL 不携带 PKCE 参数。
- “获取 user_access_token v3”页面注明 `code_verifier` 仅在“使用 PKCE 时”为必填项，即默认不使用 PKCE 的流程受官方支持。
- 飞书开放平台创建的应用均为 Confidential Client，`client_secret` 为必填认证方式（v3 令牌页面原文）；PKCE 是 Public Client 的可选增强。
- 处理：移除授权链接中的 `code_challenge`/`code_challenge_method` 和令牌请求中的 `code_verifier`，保留 `state` 防 CSRF 与 `client_secret` 客户端认证。`feishu_oauth_states.pkce_verifier_encrypted` 列保留但不再写入。
